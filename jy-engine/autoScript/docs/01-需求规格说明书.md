## 1. 引言

### 1.1 目的

本文档定义 AutoScript 全自动脚本生成套装（基于 Trae AI IDE）的功能需求与非功能需求，作为架构设计、详细设计和开发验收的依据。

### 1.2 范围

AutoScript 覆盖从"用户给出自然语言目标"到"输出可运行 JY-Frame 脚本"的完整链路，包括设备连接、界面感知、任务规划、自主操作、结果验证、状态记忆和脚本编译。

### 1.3 读者

- 项目开发者
- 架构师
- 测试人员

## 2. 项目背景与目标

### 2.1 背景

JY-Frame 框架将图色脚本开发规范化为"特征 + 任务模块"的 `taps` 表结构，但编写脚本仍需人工完成：
- 手动截图、抓色点、裁剪图片
- 手动设计任务模块边界和跳转逻辑
- 手动调试特征稳定性

这些重复劳动占脚本开发 80% 以上时间。

### 2.2 目标

构建一套基于 Trae AI IDE 的脚本生成工具套装，由 Trae AI 助手按规则自主调用 Python 脚本，自动完成上述全部工作：

| 目标 | 衡量标准 |
|------|---------|
| 零人工干预 | 用户仅输入自然语言目标，AI 自主调度脚本跑完整个流程 |
| 特征自动生成 | ps/ft/pic/ocr 特征行由脚本自动采样、验证、生成 |
| 任务自动拆解 | 任务模块边界、跳转逻辑由 AI 自主规划 |
| 脚本可运行 | 编译输出的 JY-Frame 脚本可直接在目标平台运行 |
| 失败自恢复 | 操作失败时自动重试、回退、重新规划，不中断 |
| Trae 原生集成 | 作为 Trae 项目打开即可使用，无需独立部署 |

### 2.3 不在范围内

- 不做游戏协议层分析（纯图色/节点操作）
- 不做越狱/root 相关功能
- 不做脚本的商业分发和账号管理（复用 JY-Frame 已有能力）

## 3. 用户角色与使用场景

### 3.1 用户角色

| 角色 | 描述 |
|------|------|
| 脚本开发者 | 主要用户，输入目标，获取生成的脚本，可微调后使用 |
| 维护者 | 维护 Agent 的视觉模型 prompt、特征采样策略、编译模板 |

### 3.2 典型使用场景

**场景 A：生成新游戏脚本**
1. 开发者启动模拟器，打开游戏到主界面
2. 输入目标："自动刷火副本，每天刷 5 次，刷完回城补给"
3. Agent 自主运行，截图、分析、操作、验证
4. 运行完成后输出完整 JY-Frame 脚本（Lua）
5. 开发者将脚本导入懒人精灵，直接运行

**场景 B：补充已有脚本**
1. 已有脚本缺少"活动副本"模块
2. 输入目标："在主界面增加活动副本入口，活动副本刷完返回主界面"
3. Agent 自主跑完活动副本流程
4. 输出新增的 taps 模块，可合并到已有脚本

**场景 C：脚本修复**
1. 游戏更新后某特征失效
2. Agent 重新截图、重新采样特征、更新对应 taps 行

## 4. 功能需求

### 4.1 FR-01 设备连接管理

| 项 | 内容 |
|----|------|
| 编号 | FR-01 |
| 名称 | 设备连接管理 |
| 优先级 | 高 |

**需求描述：**
- 支持通过 ADB 连接安卓模拟器和真机
- 支持多设备同时连接，按序列号选择目标设备
- 自动探测设备分辨率、DPI、Android 版本
- 连接断开时自动重连，重连失败上报异常

**验收标准：**
- 能识别雷电模拟器、MuMu、夜神等主流模拟器
- 能通过 USB/WiFi 连接真机
- 分辨率探测准确率 100%

---

### 4.2 FR-02 自动截图与界面感知

| 项 | 内容 |
|----|------|
| 编号 | FR-02 |
| 名称 | 自动截图与界面感知 |
| 优先级 | 高 |

**需求描述：**
- 通过 `adb exec-out screencap -p` 获取当前屏幕截图
- 对截图进行多模态分析，输出结构化界面描述：
  - 所有可点击元素（类型、文字、位置、置信度）
  - 界面语义标签（主界面/副本选择/战斗中/背包/弹窗...）
  - 全量 OCR 文字结果
- 对每个可点击元素自动采样稳定色点（用于生成 ps 特征）
- 原生控件界面优先使用 uiautomator dump 获取节点信息

**验收标准：**
- 截图获取延迟 < 500ms
- 可点击元素识别召回率 > 90%（游戏画面）
- 稳定色点在连续 3 帧截图中匹配成功率 > 95%

---

### 4.3 FR-03 任务自动分解与规划

| 项 | 内容 |
|----|------|
| 编号 | FR-03 |
| 名称 | 任务自动分解与规划 |
| 优先级 | 高 |

**需求描述：**
- 将用户自然语言目标拆解为子任务树
- 基于当前界面状态，自主选择下一步操作
- 维护任务进度，已完成子任务标记，未完成排队
- 任务模块边界自动判定：界面切换点 = 模块边界
- 循环操作（如反复点击攻击）自动识别为模块内循环

**验收标准：**
- 能正确拆解线性流程（登录→选服→进游戏）
- 能正确识别循环操作并标记
- 每步操作有明确的决策理由（可追溯）

---

### 4.4 FR-04 自主操作执行

| 项 | 内容 |
|----|------|
| 编号 | FR-04 |
| 名称 | 自主操作执行 |
| 优先级 | 高 |

**需求描述：**
- 支持点击、滑动、长按、输入文字、返回、主页、等待等操作
- 点击坐标从感知层元素的 bbox 中心点获取
- 坐标自动进行锚点换算（真实像素 → JY-Frame 设计坐标）
- 滑动参数（起点、终点、时长）由规划层决定
- 操作执行后自动等待画面稳定

**验收标准：**
- 点击坐标落在目标元素 bbox 内
- 锚点换算结果与 JY-Frame 框架一致
- 操作执行延迟 < 100ms（ADB 命令发出）

---

### 4.5 FR-05 操作结果验证

| 项 | 内容 |
|----|------|
| 编号 | FR-05 |
| 名称 | 操作结果验证 |
| 优先级 | 高 |

**需求描述：**
- 操作后自动截图，通过三重验证判断是否成功：
  1. 画面变化检测（感知哈希差异）
  2. 语义验证（视觉模型判断是否进入预期界面）
  3. 元素验证（预期元素出现/消失）
- 验证失败时自动处理：
  - 画面没变化 → 等待后重试，换点
  - 进入非预期界面 → 记录异常，back 回退，重新规划
  - 连续失败 3 次 → 标记子任务无法完成，跳过继续

**验收标准：**
- 成功操作验证准确率 > 95%
- 失败操作能在 3 次重试内识别并处理
- 不出现无限循环（有循环检测机制）

---

### 4.6 FR-06 状态记忆与去重

| 项 | 内容 |
|----|------|
| 编号 | FR-06 |
| 名称 | 状态记忆与去重 |
| 优先级 | 中 |

**需求描述：**
- 所有见过的界面状态存入 SQLite，按感知哈希去重
- 重复出现的界面复用已有特征和操作记录，不重复分析
- 维护状态转移图（from_state → to_state，action，success_count）
- 检测状态循环（A→B→A），发现后跳出并标记异常
- 任务分解树和完成状态持久化存储

**验收标准：**
- 相同界面重复出现时，感知层调用次数减少 > 80%
- 状态循环能在 2 轮内检测到
- Agent 异常退出后可恢复任务进度

---

### 4.7 FR-07 脚本自动编译

| 项 | 内容 |
|----|------|
| 编号 | FR-07 |
| 名称 | 脚本自动编译 |
| 优先级 | 高 |

**需求描述：**
- 将 Agent 的状态机 + 操作轨迹编译为 JY-Frame `taps` 表
- 映射规则：
  - 界面状态 → 任务模块 `taps.状态名`
  - 可操作元素 + 稳定色点 → `ff="ps"` 特征行
  - 状态转移 → `运行后方法="下一模块"` 或 `out=true`
  - 循环操作 → `ff="ps_s"`
  - 等待界面 → `ff="ps_w", waitOut=...`
- 编译时"去探索化"：只保留成功路径，去掉失败重试和探索噪音
- 自动插入防卡死配置（超时时间、无特征次数、卡屏检测）
- 支持多平台输出：Lua（懒人精灵）、VB（按键精灵）、JS（AutoJS）、Go（AutoGo）

**验收标准：**
- 编译输出的脚本语法正确，可通过框架加载
- 脚本在模拟器上运行成功率 > 90%（与 Agent 手动跑通的路径一致）
- 特征行的色点参数与 Agent 采样结果一致

---

### 4.8 FR-08 异常处理与防卡死

| 项 | 内容 |
|----|------|
| 编号 | FR-08 |
| 名称 | 异常处理与防卡死 |
| 优先级 | 高 |

**需求描述：**
- 随机弹窗（公告、活动、更新提示）自动识别并处理
- 掉线、断网、加载超时自动检测并恢复
- Agent 自身卡死（无特征、循环、超时）自动跳出
- 所有异常界面记录到异常库，编译时自动插入弹窗处理模块
- 关键操作失败时保存截图和日志，供人工排查

**验收标准：**
- 常见弹窗（公告、活动、更新）能自动关闭
- Agent 连续运行 1 小时不出现无限卡死
- 异常截图和日志完整可追溯

## 5. 非功能需求

### 5.1 性能需求

| 指标 | 要求 |
|------|------|
| 单轮循环（感知→执行→验证）耗时 | < 5s（含视觉模型调用） |
| 截图获取 | < 500ms |
| 稳定色点采样 | < 200ms |
| 脚本编译 | < 5s |
| 支持同时连接设备数 | ≥ 3 |

### 5.2 可靠性需求

- Agent 连续运行 1 小时无人工干预不崩溃
- 操作失败自动恢复率 > 80%
- 生成脚本在目标平台运行成功率 > 90%

### 5.3 可扩展性需求

- 视觉模型可插拔（支持豆包视觉、Qwen-VL、GPT-4V 等）
- 输出平台可扩展（新增平台只需加模板）
- 特征采样策略可配置（色点数量、偏色算法等）

### 5.4 兼容性需求

- 支持 Windows 10/11（开发和运行环境）
- 支持主流安卓模拟器（雷电、MuMu、夜神）
- 支持 Android 7.0+ 真机
- 输出脚本兼容 JY-Frame v1.0+
- **Trae 兼容性**：作为 Trae 项目打开，AI 能正确读取 rules.md 和 soul.md 并自主调用脚本
- **迁移兼容性**：核心脚本（scripts/）不依赖 Trae，可迁移至 AIStruct 等其他 AI 宿主

### 5.5 可维护性需求

- 模块化设计，各层职责清晰
- 核心数据结构和接口有完整文档
- 关键操作有日志记录（截图 + 决策理由 + 验证结果）

## 6. 用例描述

### 用例 UC-01：生成刷副本脚本

| 项 | 内容 |
|----|------|
| 用例名 | 生成刷副本脚本 |
| 参与者 | 脚本开发者 |
| 前置条件 | 模拟器已启动，游戏在主界面，ADB 已连接 |
| 主流程 | 1. 开发者输入目标："自动刷火副本，刷完回城"<br>2. Agent 截图分析主界面，识别"副本"按钮<br>3. Agent 点击副本，验证进入副本选择界面<br>4. Agent 识别"火副"按钮，点击，验证进入战斗<br>5. Agent 在战斗中循环点击攻击，验证战斗结束<br>6. Agent 点击回城，验证回到主界面<br>7. Agent 编译状态机，输出 JY-Frame Lua 脚本 |
| 异常流程 | 步骤 3 点击后没反应 → 等待重试 → 换点 → 仍失败则 back 回退重新规划 |
| 后置条件 | 输出可运行的 Lua 脚本文件 |
